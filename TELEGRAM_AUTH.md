# Вход через Telegram

Почта и пароль из приложения убраны. Аккаунт создаётся из профиля Telegram:
мини-приложение отдаёт подписанную строку `initData`, сервер проверяет подпись
токеном бота и открывает обычную сессию Supabase.

## Что нужно сделать один раз

### 1. SQL в Supabase

Supabase → SQL Editor → выполнить `supabase_telegram_auth.sql`
(добавляет `profiles.telegram_id` и уникальный индекс по нему).

### 2. Переменные окружения на Vercel

Project Settings → Environment Variables. Все три — **серверные**, без префикса
`VITE_`, иначе они уедут в браузер:

| Переменная | Где взять |
|---|---|
| `TELEGRAM_BOT_TOKEN` | @BotFather → токен бота, которому принадлежит мини-приложение |
| `SUPABASE_URL` | Supabase → Project Settings → API → Project URL (тот же, что во `VITE_SUPABASE_URL`) |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Project Settings → API → `service_role` ключ |

`service_role` ключ обходит RLS. Он используется только в `api/telegram-auth.js`
и не должен попадать в клиентский код.

После добавления переменных нужен redeploy — на лету они не подхватываются.

### 3. Email-провайдер в Supabase

Auth → Providers → Email должен быть включён. Письма никуда не уходят: сервер
пользуется `generateLink` только чтобы получить одноразовый токен входа.

## Как это работает

1. Telegram кладёт в мини-приложение `window.Telegram.WebApp.initData` —
   строку с данными пользователя, подписанную ключом бота.
2. Клиент отправляет её на `POST /api/telegram-auth`.
3. Сервер пересчитывает HMAC-SHA256 по документации Telegram и сверяет с
   `hash`. Подделать подпись без токена бота нельзя. Строки старше часа
   отклоняются: `initData` сразу меняется на обычную сессию Supabase, которая
   дальше живёт сама, поэтому держать окно шире незачем.
4. По `telegram_id` находится или заводится пользователь Supabase, при первом
   входе создаётся строка в `profiles` (ник из `@username`, аватарка из
   `photo_url`).
5. Сервер возвращает одноразовый `token_hash`, клиент меняет его на сессию
   через `supabase.auth.verifyOtp`.

Технический адрес пользователя — `tg<telegram_id>@telegram.local`. Письма на
него не отправляются, человеку он не показывается.

Адрес предсказуем, поэтому вход разрешён только когда найденная запись
действительно привязана к этому `telegram_id`. Если пользователь с таким
адресом уже есть, а привязки у него нет, сервер отвечает `409
account_conflict` и сессию не выдаёт: иначе, зарегистрировавшись заранее на
чужой `tg<id>@telegram.local`, можно было бы дождаться первого входа
владельца и получить его аккаунт.

Ответы об ошибках содержат только код. Подробности пишутся в журнал функции;
чтобы вернуть их и в теле ответа при отладке, задайте `AUTH_DEBUG=1`.

Частота ограничена: не больше двадцати запросов за пять минут с одного адреса
и столько же на один `telegram_id`.

Вход происходит автоматически при запуске приложения внутри Telegram. Кнопка
«Войти через Telegram» в профиле нужна на случай, если автовход не прошёл.

## Ограничения

- Вне Telegram войти нельзя: `initData` есть только внутри клиента Telegram.
  В браузере кнопка входа неактивна, остальное приложение работает.
- `vite dev` не поднимает `/api` — локально вход не проверить, нужен
  `vercel dev` или деплой.
- Профили, заведённые по старой почтовой схеме, остаются в базе. При первом
  входе через Telegram человек получит новый профиль; связать старый с
  `telegram_id` можно только вручную в базе.

## Что выполнить в Supabase

Кроме `supabase_telegram_auth.sql` — ещё два файла, они закрывают запись
чужим:

- `supabase_storage_policies.sql` — писать в хранилище можно только в свою
  папку (первый сегмент пути равен идентификатору пользователя). Без этого
  любой вошедший может перезаписать `metadata.json` чужого токена и подменить
  его имя, символ и картинку.
- `supabase_tokens_policies.sql` — читать таблицу токенов может кто угодно,
  заводить, править и удалять строку — только её владелец.
